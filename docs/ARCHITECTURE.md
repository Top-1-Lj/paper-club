# 架构与关键决定

## 结构

应用采用 Django 服务端渲染。URL 路由分派到 `club.views`，表单通过 `club.forms` 校验，业务数据存储在 SQLite，页面由项目内的 Django 模板和静态样式构成。导出转换独立放在 `club.exports`，便于测试和后续复用。

项目使用单个 Django 应用组织共读业务，配置、模板与静态资源保持独立。对外链接只保存地址；论文录入不抓取远程页面，使用已安装的应用不依赖模型服务。

## 数据关系

```text
User ── created_by ── Paper
User ── author ────── ReadingCard ── paper ── Paper
User ── user ──────── ReadingProgress ── paper ── Paper
User ── author ────── Comment ── card ── ReadingCard
ImportedPaper ── paper ── Paper
ImportedPaper ── card ─── ReadingCard
```

- `Paper` 保存文献元数据、原文链接和录入者。
- `ReadingCard` 保存一名用户对一篇论文的结构化笔记。数据库唯一约束保证同一用户对同一篇论文只有一张卡片，不同用户可分别写卡。
- `ReadingProgress` 独立记录 `(user, paper)` 的未读、在读或已读状态。状态不放在 `Paper` 上，避免一位同学更新后影响所有人；也允许先记录状态再写卡片。
- `Comment` 关联具体卡片和作者，形成围绕阅读理解的讨论。
- `ImportedPaper` 保存导读来源、固定标识和字段快照，用于重复导入和保留人工修改。
- 卡片与评论的 `is_demo` 明确标识样例内容，导出样例卡片时同样说明。

模型使用稳定的数据库主键作为关联与页面标识，避免把可修改标题或用户名当成关联键。`created_at` 与 `updated_at` 为展示和后续同步提供时间信息。

## 公开范围与权限

首版所有论文、卡片和评论均公开可读，包括相应导出。登录是写入操作的前提，用户只能更新自己的阅读状态、卡片和评论；论文由录入者维护。

权限在后端根据当前会话用户和对象归属检查。隐藏按钮仅用于界面清晰，直接请求其他用户的编辑、删除或状态地址也必须经过后端验证。表单包含 CSRF 保护，删除等写入操作通过 POST 完成。

“我的卡片”是当前用户内容的筛选入口，不是私密内容存储。未来如果引入私密或组内可见内容，需要把可见性条件同时应用到列表、详情、搜索、评论和导出。

## 删除策略

`ReadingCard.paper` 使用 `PROTECT`，有卡片关联时数据库层拒绝删除论文；页面在删除前也给出提示。论文录入者不能通过删论文间接清空其他人的卡片。

删除卡片会级联删除该卡片下的评论，因此页面需要明确确认。每个用户的阅读状态独立于卡片，删除卡片不代表用户从未读过这篇论文。论文最终删除时，其阅读状态随之删除。

`Paper.created_by` 同样使用 `PROTECT`，避免删除用户时无声丢失其论文条目。管理员批量处理账户或数据时需要遵循这些关系。

## 校验、搜索和导出

论文通过表单校验标题、年份、作者、摘要、网址及可选字段。作者推荐使用分号分隔；标签使用逗号规范化保存。检索由数据库查询执行，列表分页保留筛选条件。

Markdown 导出保留中文和六个结构化字段，并包含论文地址、作者和更新时间。BibTeX 导出由单独函数转义特殊字符，字段缺失时按可选字段处理。导出是下载文本，不执行用户输入的内容。

## 演示初始化

`seed_demo` 在事务内运行。先检查 `lin`、`chen` 是否为带有专属邮箱标记的演示账号，遇到同名其他用户则拒绝整次写入。首次创建账号时设置初始密码，之后不重置密码。

论文按不可编辑的 `demo_key`（例如 `arxiv-1706.03762`）复用；修改标题或原文链接不会改变初始化标识。首次升级旧样例时，只给专属演示账号名下且原始链接匹配的条目回填标识，不认领普通用户的同链接论文。卡片按 `(paper, author)` 复用，演示评论按 `(card, author, is_demo=True)` 复用。使用 `get_or_create` 的默认值只填充新记录，不覆盖已有修改。编辑演示内容时保留示例标记，维持可追溯性和重复初始化的一致性。

基础示例的元数据来自 arXiv，年份使用首次预印本年份；对应笔记与评论保留演示标识。附来源的导读数据通过 `import_papers` 单独导入，记录正式出版信息、证据位置及核对说明，详见 [导读数据文档](CURATED_IMPORT.md)。

## 后续接入社区

当前项目提供独立页面与会话登录，没有提前假定社区统一接口。接入时可逐步进行：

1. 确定总平台用户标识到本地 `User.id` 的映射，接入学校或社区登录。
2. 在现有表单、查询和导出逻辑周围添加明确版本的 API，保留稳定的 `paper_id`、`card_id` 和 `user_id`。
3. 将 SQLite 切换为 PostgreSQL，保留迁移历史并制定数据迁移与备份流程。
4. 按团队要求增加内容可见性、审核、访问审计和备份。

文献自动导入、PDF 解析或 AI 问答可以作为独立模块加入。当前的 `paper_url` 和结构化笔记提供内容入口，相关能力应有自己的接口、错误处理和验证标准。

## 本机与服务器边界

默认 `runserver` 绑定本机回环地址，目标是本机演示。固定依赖、迁移和样例初始化用于复现；服务器部署另行配置正式密钥、允许主机、静态文件与 WSGI / ASGI 服务。

配置读取当前进程的环境变量，`.env` 仅为示例时不会自动生效。`PAPERCLUB_DB_PATH` 可以指定另一数据库，便于在保留已有数据的同时使用独立演示库。
